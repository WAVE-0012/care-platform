## 老人档案与能力评估

社区管理员以身份证唯一检索值建立老人档案，登记授权联系人，组织能力评估，并按能力等级选择服务包和责任护工。老人及家属查询自己的评估、照护计划和服务记录。迁移社区时沿用原档案编号，避免同一人重复建档。

档案、联系人和评估页面作为边界对象；业务服务完成身份去重、授权有效期与评估资格判断；老人、联系人、评估、服务包、照护计划和计划项目构成实体对象。控制对象先选择服务日期之前最新的评估，再检查有效期，不会跳过已过期的新评估重新采用旧记录。

同一老人同一时段只能有一份生效照护计划。评估到期后，维护过程将计划置为暂停，并把未开始服务的派单释放回调度池。下单和派单仍会即时核验评估，维护进程两次执行之间也不能继续使用过期资格。计划已经用于服务后，其项目频次和相关评估记录冻结。

老人到联系人、能力评估和照护计划均为一对多。服务包与服务项目通过 package_item 连接，照护计划与服务项目通过 plan_item 连接，关联表保存频次和周期。计划项目是制定计划时的事实，后续服务包目录变化不会改写已用计划。

## 服务下单与派单

老人、有效授权家属和社区管理员可以预约服务、取消订单并查看进度。社区负责候选护工查询和人工派单。护工接单、到场服务并填写记录，老人或家属确认后结算。管理员改派时填写原因，系统保留旧派单记录及名额释放情况。

订单页与详情页承接预约、派单和确认操作；资格计算、候选筛选、派单事务和结算过程承担控制逻辑；订单、派单、班次、工时和准入依据保存业务事实。服务地址与下单时社区、价格、时长一并保存，后续迁移或改价不会改变历史账目。

派单同时检查能力评估、照护计划、服务区域、资质有效期、在岗与培训状态、班次覆盖、剩余名额、已有服务冲突和整改限制。接单超时后释放名额。完成订单需要有效工时、服务记录和确认信息；确认接口重复调用不会重复累计金额与工时。

老人和服务项目分别与订单构成一对多关系。订单到派单是历史上的一对多，过滤唯一索引只约束“当前派单”最多一条。派单关联班次，班次关联护工；工时通过派单连接服务过程。准入依据以订单编号为主键，形成一对零或一的服务资格快照。

## 护工与排班

机构负责人登记护工、培训和证书，分配可服务项目与社区，发布班次及可接单量。护工查看本人班次和订单，服务前后签到签退。位置、时段或时长异常的工时进入复核队列，由机构负责人填写认定工时和核验说明。

护工、排班和工时页面作为边界；排班发布过程、候选计算函数、围栏计算和工时复核过程构成控制；护工、证书、服务项目关联、服务区域关联、班次、派单和工时构成实体。排班与派单使用同一护工行锁，使冲突检查和名额扣占处于一个事务内。

班次采用左闭右开区间，前一班结束时刻可等于后一班开始时刻。班次容量必须为正，使用名额不能大于容量；已有派单的班次时段不能直接修改。围栏校验使用地理距离，自动工时同时要求时段和位置正常。人工认定工时不得超过实际签到签退跨度，服务人不能审核自己的异常工时。

机构到护工、护工到证书和班次均为一对多。护工与服务项目、社区之间为多对多，分别转换为 worker_skill 和 worker_area 两张复合主键表。派单到工时最多一条，既避免重复签到，又保留异常工时的复核结果。

## 健康监测与应急响应

社区登记设备并绑定老人，设备接口成批上传体征。家属和工作人员可核实异常、发起求助。值班人员接到事件后登记响应、到场和处置结果。维护进程扫描超时事件并升级通知，发送失败累计三次后转人工处理。

设备上传接口、健康列表和应急工作台是边界；绑定区间检查、阈值判断、事件处理和超时升级是控制；设备、绑定记录、指标规则、体征、应急事件及通知记录是实体。上传时按采集时刻寻找绑定，并以绑定、指标规则和采集时刻去重。

同一设备的绑定区间不能重叠。晚到数据仍属于采集时刻对应的老人，历史绑定和已使用阈值不可修改。阈值触发器按 inserted 集合处理多行，先校验阈值属于老人当前社区，再按上下限标记越界读数。应急不受照护计划过期限制，响应、到场、关闭依次推进；首次超时升级只生成一轮对应通知。健康阈值为课程演示配置。

设备到绑定记录、老人到绑定记录均为一对多；绑定记录到体征是一对多。体征连接指标规则，不直接保存当前设备归属。应急事件可以关联一条异常体征，也可以由家属主动发起；事件到通知是一对多，通知按对象和阶段去重。

## 补贴核算与服务质量监管

社区在次月按老人、项目和自然月归集已完成服务，提交补贴依据。街道初审后转民政终审，终审通过后登记拨付。退回申报修改材料后重新提交，既有审核轮次继续保留。监管人员抽查服务，机构提交整改结果后，由监管复核解除限制。

申报、审核和整改界面作为边界；政策匹配、金额归集、分级审核、拨付与整改限制是控制；政策、申报、明细、审核记录、质量抽查及已完成订单是实体。申报明细逐笔保存订单、政策版本和金额，审核记录保存每一轮阶段与意见。

同一老人、项目和月份只能存在一份申报，每笔订单只能进入一条申报明细。只有完成、工时有效且证据完整的订单进入核算，政策按服务发生时间与区县匹配。申报金额采用逐笔金额求和，并不把多条审核记录直接连入金额聚合。拨付流水号唯一，重复请求不重复拨付；未完成整改的护工或机构按限制范围暂停接单。

申报与订单通过 claim_item 关联，一份申报包含多条明细，每笔订单只能申报一次。明细连接具体政策版本；申报与审核记录为一对多。质量抽查关联护工并可关联订单，限制范围可以落到项目或机构，整改状态参与候选护工计算。

## 范式与历史快照

实体转成独立关系表，表的编号作为主键；一对多联系把父表主键放入子表作为外键；多对多联系转换为关联表。worker_skill(worker_id,item_id)、worker_area(worker_id,community_id)、package_item(package_id,item_id)、plan_item(plan_id,item_id)使用复合主键，避免同一关联重复出现。带历史的联系增加独立编号和时间字段，典型例子是 assignment 与 device_binding。

基础资料满足原子性：姓名、时间、金额和状态分别存储，项目清单没有保存为逗号分隔字符串。关联表中的频次依赖完整的“计划、项目”或“服务包、项目”组合，不依赖复合键的一部分，因此满足第二范式。机构信息、社区信息、证书与项目名称各自存入对应表，引用处只保留外键，消除可变基础资料的传递依赖，基础关系达到第三范式。

以派单为例，assignment.id决定order_id、shift_id、状态、接单时间和服务记录；shift_id所对应的护工姓名与机构名称不重复写入派单表。以申报明细为例，订单编号唯一，明细连接申报与政策，不在申报主表重复保存订单列表。过滤唯一索引只对满足条件的记录保证唯一，例如 is_current=1 的派单；它不构成整个历史关系的候选键。

基础关系按第三范式设计，物理实现为查询和结算保留少量受控冗余：班次已用名额、护工累计工时与评分、订单结算额、申报总额和体征异常标记。名额和累计工时由集合式触发器维护，金额由结算或申报过程计算，已完成记录冻结，并以复验查询检查汇总一致性。

订单的服务地址、发生时社区、单价和标准时长，准入快照中的评估、计划和低保资格，以及申报明细中的政策版本描述的是发生时的业务事实。它们与当前档案、目录及政策的值可以不同，因此不能按当前值的依赖关系直接删除。保留快照后，服务完成时的规则和金额可以独立复核。

## 非功能性需求

### 身份与访问范围

用户使用八类固定角色。社区账号访问本社区，机构访问本机构护工及其业务，街道和民政按区划查看；家属按授权有效期访问对应老人，护工按当前派单访问服务对象。页面菜单只负责展示，服务端对每个操作重新判断角色和数据归属。

### 机密性与登录安全

密码使用 PBKDF2-SHA256 和独立随机盐，迭代 600000 次。连续五次失败锁定三十分钟，会话空闲三十分钟失效。身份证和电话使用 Fernet 加密，身份证另保存带密钥的 HMAC 用于唯一检索，列表仅返回脱敏值。会话签名和加密密钥保存在实例目录。

### 事务与并发一致性

一次业务请求使用一条连接和一个事务。派单按订单、护工的固定顺序获取更新锁，锁内再次验证班次名额与时间冲突。唯一约束和集合式触发器阻止重复当前派单、重复申报、重叠区间和冻结历史的修改。异常导致整个业务事务回滚。

### 状态与时间口径

日期有效期含截止当日，班次和设备绑定采用左闭右开区间。服务资格按照服务日期判断，设备归属按照采集时间判断，补贴按照服务发生月份与政策版本判断。订单、应急和申报各有显式状态，操作接口只允许对应的前序状态。

### 可追溯与可维护性

改派、审核、整改和重要状态变化写入审计记录。五条业务线分别放入 services 模块，Repository 只封装通用数据库读写。数据库对象按表、视图函数、过程、触发器、权限顺序部署，业务错误转换为可读中文提示，数据库连接及事务由统一上下文管理。

### 性能与恢复

列表采用每页二十条的分页，常用访问路径设置复合与覆盖索引。性能验证单独使用十万行临时表，避免扩充演示库。备份采用完整、差异和日志组合，恢复到新库后验证数据库完整性以及人数、订单、工时和金额。

## 查询实现比较

### A1 有效计划中的重度失能老人及护工

APPLY 为每位老人查最新评估；窗口函数先给所有评估编号再取第一条。前者适合按少数老人过滤，后者适合全社区批量统计；两者均先取最新评估再检验有效期。

### A2 七天内到期的最新评估

NOT EXISTS 排除存在更晚评估的记录；左连接把不存在更晚评估表示为右表空值。日期窗口与排除条件相同，反连接方式更贴近本查询的“不存在”含义。

### A3 社区各等级在册人数

相关子查询逐社区、逐等级统计；预聚合一次计算全部人数后左连接等级全集。预聚合减少重复扫描，COALESCE 保证零人数等级仍显示。

### B1 订单最终服务人及历史派单次数

直接连接当前派单并相关统计历史次数，与分层 CTE 先计算当前服务和历史次数的结果相同。LEFT JOIN 保留未派订单；过滤唯一索引保证当前派单最多一条。

### B2 超过十五分钟未接单的订单

EXISTS 判断当前派单是否超时；连接写法直接取得同一条当前派单。条件均要求订单和派单仍为待接单状态，当前派单唯一保证连接不产生重复行。

### B3 待确认订单缺失的完成条件

视图使用 CASE 逐列标记缺记录、缺确认和缺工时；第二版将各缺项用 UNION ALL 组合，再通过条件聚合返回相同三列。视图适合页面，分项写法便于增加新的缺项类型。

### C1 护工月度有效工时及服务结果

条件聚合在一个分组中计算订单数、完成数、有效工时和投诉数；另一版按全部服务和已完成服务分别聚合后连接。均以当前派单和护工月份为粒度，取消订单不计入分母。

### C2 持有效中级及以上护理证的在岗护工

EXISTS 表达是否存在满足条件的证书；JOIN 加 DISTINCT 消除同一人多张证书造成的重复。两版按当天日期检查证书有效期，EXISTS 更直接表达资格筛选。

### C3 班次保存名额与现场重算名额

视图用相关聚合重算名额；另一版先按班次分组再连接。两版都同时返回保存值和计算值，统计包括有效派单以及已产生工时的终止派单，可作为一致性复验。

### D1 街道应急响应统计

直接连接事件、社区和街道后分组，与先按社区汇总再合并街道的结果相同。平均值以已响应样本数为分母，用累计秒数加权，不能直接对社区平均值再平均。

### D2 指定老人历史体征

直接连接体征、绑定和指标规则，与先筛选老人绑定再连接读数的 CTE 写法相同。两版都通过历史绑定确定归属，设备当前绑定不参与结果判断。

### D3 响应超时或通知失败的未关闭事件

EXISTS 检查失败或转人工通知；另一版先把失败通知按事件去重，再左连接。两版都用 OR 合并响应超时和发送失败，且排除已关闭事件。

### E1 申报明细的政策工时和审核次数

一版为每条明细相关统计申报审核次数，另一版先按申报汇总审核记录后再连接。结果粒度为申报明细，审核次数作为单值附加，避免多轮审核复制明细金额。

### E2 当前受到整改限制的护工

两路 EXISTS 分别检查个人限制与机构限制；UNION 写法先合并两类受限护工，再连接档案。UNION 去重保证同时命中两类限制时只返回一次。

### E3 完成订单的核定补贴和自付

LEFT JOIN 保留所有完成订单，只有 approved 或 paid 的申报计入核定补贴。另一版用 UNION ALL 分开处理已申报与未申报订单。输出按订单粒度保留，核定金额与实际拨付状态分开查询。

## 运维与风险

### 工程与版本管理

项目按业务服务、数据库脚本、测试、运维脚本和证据目录组织。本地 Git 保存本次实际文件版本，提交记录可通过 git log 查看。数据库元数据用于生成关系模式和图，减少多份手工材料之间的差异。成员分工、会议和答辩反馈分别留出独立记录位置。

### 完整与差异备份

运行环境采用完整恢复模式。计划每周日 02:00 做完整备份，每日 02:00 做差异备份，每十五分钟做日志备份，保留最近四周的可恢复链。每月选择一条链恢复到独立数据库；备份文件和 instance/keys.json 分别加密保存，再复制到另一介质。周期为部署方案，当前已实际执行一次完整、差异、日志恢复演练。

### 恢复目标与步骤

部署目标为 RPO 不超过十五分钟、RTO 不超过三十分钟。先确定最后可用完整备份，依次恢复差异和后续日志，最后 RECOVERY；必要时先备份故障前尾日志。恢复后执行 DBCC CHECKDB，核对老人和订单数、结算额、工时与申报额，再切换连接配置。目标值需要在实际数据规模及备份介质上持续演练。

### 权限与密钥

应用事务切换到无登录用户 care_app，仅授予业务表读写和过程执行权限，禁止结构变更；审计与审核记录禁止更新和删除。Windows 集成连接用于本机课程运行，部署时应使用独立 Windows 服务账号承载连接。Web 会话使用 HttpOnly、SameSite Cookie，修改请求携带 CSRF 令牌；参数值均通过占位符绑定。密钥文件不进版本库，备份恢复时同时核对其可用性。

### 运行维护

start.ps1 启动 Web 服务和每分钟维护进程。维护脚本处理计划到期、派单超时、应急升级和通知重试并记录结果。日常检查关注待响应事件、超过三次发送失败的通知、待工时复核、未完成整改和待审核申报。服务器正式部署时可由 Windows 任务计划程序按约定周期运行备份命令；本项目不预设操作系统级定时任务。

### 问题一 资格与历史冲突

老人迁移、评估更新和价格调整会影响当前资料，但不应重算既有服务。解决方案是在订单和准入依据中保存发生时快照，完成后冻结；设备历史采用有效期绑定。测试覆盖最新评估失效、换绑后的迟到读数、历史修改被拒绝等情形。

### 问题二 并发与重复提交

应用页面上的可用名额在提交时可能已改变。解决方案是在数据库事务内锁定订单和护工，再检查候选资格；过滤唯一索引限制当前记录数量。订单请求键、结算状态和拨付流水分别承担幂等控制。测试以两条独立连接同步竞争最后一个名额，并验证一次成功、一次拒绝。

### 问题三 关联统计重复计数

一笔申报可以有多条明细和多轮审核，直接连接后求和会放大金额。解决方案是将明细金额和审核次数分别汇总到申报粒度，再连接展示。十五组 SQL 的两种实现使用相同数据和排序口径比较，金额统计还与恢复后的数据库汇总交叉核验。
