# 对象与口径映射（2026-11-17 复核后）

本文件解决三类口径冲突：**设计实体 37 vs 物理表 33**、**文档视图 16 vs 物理视图 17**、**文档过程/触发器 5+5 vs 物理 11+15**。以后报告、答辩和数据字典统一使用本文件的“物理口径”；37 个设计实体保留为分析口径，不再当作物理表数量。

## 1. 物理口径（以数据库为准）

| 对象 | 数量 | 说明 |
| --- | ---: | --- |
| 表 | 33 | 33 PK、276 字段、70 FK、18 UK、82 CHECK、45 DEFAULT |
| 索引 | 17 | 11 个普通非唯一索引 + 6 个过滤唯一索引（另有 33 PK、18 唯一约束） |
| 视图 | 17 | 档案 3、订单 3、排班 3、健康 4、补贴 4 |
| 存储过程 | 11 | 见第 4 节逐项映射 |
| 触发器 | 15 | 见第 5 节逐项映射 |

数据来源：`docs/evidence/database_inventory.json`、`docs/design/data_dictionary.json`。

## 2. 37 个设计实体 → 33 张物理表

| 设计实体（业务分析 §12） | 物理实现 | 变化与影响 |
| --- | --- | --- |
| E05 角色、E06 用户角色 | `app_user.role`（8 值枚举） | 2 表 → 1 列；**一人只能一个角色**，不能同时是社区工作人员和家属账号 |
| E27 事件等级时限 | `emergency.level` + `response_minutes` + `arrival_minutes` | 1 表 → 3 列；等级时限不再集中配置，每个事件保存一份 |
| E35 事件体征关联 | `emergency.vital_id` + `UX_emergency_vital` | 1 表 → 1 列；**多对多变为 1:1**，一个事件最多关联一条体征 |
| 其余 33 个实体 | 33 张表一一对应 | 无变化 |

结论：**37 = 33 + 4**，不是漏建 4 张表。报告第二章/第四章要写清 4 处折叠及其范式影响，答辩时按本表回答“用户角色表去哪了”。

## 6. §12 字段清单与物理表差异（本轮不补列）

业务分析 §12 是**设计数据项**，物理表按实现需要做了裁剪。以下 9 张表共 34 列未落库：

| 表 | §12 列出但物理表没有的列 | 影响 |
| --- | --- | --- |
| `service_order` | 入调度池时间、评价时间、投诉时间、投诉处理状态（4） | 投诉处理状态无法落库；评价/投诉只有内容没有时间 |
| `assignment` | 确认联系人、确认方式、签字凭证摘要、凭证录入人（4） | 纸质确认与电子确认无法区分；凭证被替换无法发现 |
| `vital` | 确认人、确认时间、确认说明（3） | 只能靠 `audit_log` 追溯，体征行本身没有核实人 |
| `emergency` | 事件类别、上报人、首次成功通知时间、关闭人（4） | 关闭事件查不到关闭人；无法按类别统计 |
| `quality_check` | 公示状态、公示时间、公示摘要、复核时间（4） | §12.33 的公示功能没有数据 |
| `audit_log` | 请求编号、变更前摘要、变更后摘要、原因（4） | 只能按 `detail` 文本检索，不能按请求号串一次操作 |
| `notification` | 通用业务类型/编号、接收用户/联系人、渠道、创建时间、成功时间、下次重试时间（约 7） | `event_id NOT NULL`，只能记应急通知，记不了复评提醒/调度通知 |
| `metric_rule` | 来源说明、是否启用（2） | 阈值来源和停用无法表达 |
| `device` | 当前档案编号、绑定时间（2） | 物理实现把当前绑定放在 `device_binding`（`unbound_at IS NULL`），与 §12.23/§12.24 的“当前绑定在设备表”说法冲突 |

**裁定**：物理字段以 `docs/design/数据字典与关系模式.md` 为准；§12 保留为设计数据项清单。报告第二章描述功能时，不要承诺上表未落库的字段；如要补，必须同时补应用写入、种子数据和测试，属于下一轮模型扩展。

## 7. 类型/语义变化（报告需解释）

| 设计口径 | 物理口径 | 说明 |
| --- | --- | --- |
| 能力等级“字符型” | `assessment.ability_level tinyint 0–3` | 枚举编码，CHECK 限制范围 |
| 事件等级“字符型” | `emergency.level tinyint 1–3` | 同上 |
| 指标阈值主键=指标类型 | `metric_rule.id`，`UNIQUE(community_id, metric)` | 按社区配置阈值；一个社区一种指标一条，使用后不可改 |
| 事件体征关联多对多 | `emergency.vital_id` 1:1 | 一个事件最多一条主因体征 |
| 用户角色多对多 | `app_user.role` 单值 | 一人一角色 |
| 设备当前绑定在设备表 | `device_binding.unbound_at IS NULL` | 当前与历史绑定同表，按区间区分 |

## 8. 尚未修复项（按风险排序）

| 项 | 原因 | 建议 |
| --- | --- | --- |
| 指标阈值多版本 | 需要给 `metric_rule` 加生效区间并改 `health.upload` 的取规则逻辑；现有测试/种子都按“一社区一指标”写 | 下一轮做 `(community_id, metric, starts_on)` + 当前版本查询 |
| 通知通用化 | `notification.event_id NOT NULL` 绑死应急；改成 `business_type/business_id` 会波及 `sp_escalate_emergencies`、`health.create_event`、视图 | 下一轮统一通知模型 |
| 34 列字段缺口 | 补列不补写入会得到一堆 NULL，反而降低数据质量 | 与报告口径二选一：裁剪 §12，或连应用一起补 |
| 同日 ADL+MMSE | 唯一键 `(elderly_id, assessed_on)` 与“一天一份最终评估”口径一致；改成含 scale 会让 `fn_eligibility` 的 TOP 1 产生并列 | 先确认业务是否要同天两量表 |
| 订单跨零点 | `CHECK` 要求预约与结束同一自然日 | 确有夜间跨零点服务再放开 |
| `subsidy_claim.draft` | 枚举存在但没有写入路径；过程遇到未完成订单直接拒绝 | 要么实现草稿，要么删枚举 |
| `sp_create_plan` 不校验责任护工资质/区域 | 责任护工可能是“偏好护工”，建计划时未必已具备全部资质；强校验会改变业务语义 | 与业务确认后再加 |
| `sp_escalate_emergencies` 并发唯一冲突 | 两个调度实例同时插入会靠唯一约束让其中一个整批回滚 | 改为 `MERGE` 或捕获 2627 重试 |
| `v_reassessment_due` 与 A2 口径不同 | 视图含“从未评估/已过期”，A2 只取未来 7 天；两者回答的问题不同 | 报告写明“运营提醒 vs 报表窗口”，不要互相校验 |
| 敏感列列级权限 | `care_app` 可读 `password_hash`/`identity_cipher`；登录需要哈希，列级 DENY 需配合登录过程 | 下一轮做 `sp_login` + 列级 DENY |
